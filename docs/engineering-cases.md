# 典型问题与工程解决案例

以下案例均来自实际开发、自动化测试、真实模型评测或手工验收，不是为了作品集补造的故事。

## 1. RAG 能回答制度条款，却答不好具体业务问题

**现象：** “去南京出差三天一共能报多少”经常直接拒答，或在城市档位、住宿晚数和供餐情况未知时给出看似确定的数字。

**根因：** 问题不只是检索召回，而是“证据存在但计算前提不完整”。单纯提高 top-k 或改 Prompt 会增加模型猜测。

**方案：** 在回答生成前加入 evidence qualification 和 clarification contract，把无证据、来源冲突、前提缺失分成不同终态。具体业务 public 质量项通过，但 Retrieval P95 3,246ms 未达到 500ms 严格门槛，性能债务被保留而不是改门槛。

## 2. HR Tool Calling 真实模型准确率偏低

**现象：** 第一版真实评测中，模型会重复读取、过早提交、选择不相关工具或遗漏参数。

**根因：** 静态暴露所有工具给模型，自由度过大；第一版 evaluator 还把多轮业务和确定性协议失败混在一起。

**方案：** 引入通用 Flow Policy、动态工具裁剪、服务端可见工具快照校验、规范化参数和单次运行 read cache。写操作仍只生成 Confirmation。48 条公开回归第七次通过，随后 20 条 seed-blind 达到原门槛。

## 3. `2026年` 被判定为 `year_invalid`

**现象：** 多轮请假中只缺年份，用户回复“2026年”仍被要求重新输入。

**根因：** Extractor 已给出候选，但 Validator 只接受纯数字形态，缺少自然中文年份到整数的确定性 canonicalization。

**方案：** 保持 LLM 只做候选，统一在 Validator 中规范化“2026年 / 年份是2026 / 就是2026年”，再与 pending 日期候选汇合；不通过 Prompt 强迫用户使用机器格式。

## 4. 已经提取字段，旧 intent gate 却没有激活草稿

**现象：** 用户首轮已经说出请假日期和原因，下一轮补类型时系统仍要求重发全部信息。

**根因：** Candidate Extraction 成功，但 Runtime 仍依赖旧的封闭 intent classifier；被判定为 `unknown` 时没有保存结构化草稿。

**方案：** 以经过验证的 slot 作为草稿激活依据，旧 intent 仅用于路由提示，不能否定已经验证的业务事实。历史跨轮信息只来自持久化草稿。

## 5. 采购 partial item 被 all-or-nothing 丢弃

**现象：** “标题为办公用品，买一个桌子，单价600”识别了标题，却把整个采购明细标成缺失。

**根因：** item-level Validator 要求 unit、category 等字段一次齐全；任一字段缺失会丢掉已经明确的 name、quantity 和 unit price。

**方案：** 把 accepted/pending/rejected 粒度下沉到 item field。明确子字段进入草稿，缺失子字段单独追问；模型不能猜单位和品类。多 item 也按稳定 item identity 合并。

## 6. rejected 新候选污染历史可信 item

**现象：** 用户修改采购内容后出现难以理解的“待补充信息”，历史中原本完整的 item 也变得不完整。

**根因：** Draft Merger 把本轮 rejected candidate 当作新事实覆盖了历史 canonical item。

**方案：** 冻结合并不变量：accepted 才能进入 canonical draft；pending 进入待确认区；rejected 只记录原因，不能破坏旧可信事实。显式冲突必须由用户闭合确认。

## 7. 采购 purpose 对自然表达召回不足

**现象：** “买显示器用于开发”“采购椅子供会议室使用”中的用途没有稳定进入草稿。

**根因：** 旧规则围绕少量固定句式设计，继续堆正则会形成封闭中文语法。

**方案：** 改为同模型 LLM-first Candidate Extraction，`source_quote` 证明字段确实来自当前输入；确定性程序再校验长度、来源和冲突。旧语义正则不作为失败回退。

## 8. Confirmation 重试一直失败

**现象：** 调休申请重复点击确认仍失败，页面不断诱导重试。

**根因：** ProductEvent 维度仍维护旧 `sick` 枚举，没有与正式 `LeaveTypeCode` 的 `annual/compensatory` 合同对齐；业务创建与事件写入位于同一事务，因此事件校验失败触发整笔回滚。

**方案：** 对齐单一业务枚举来源，保留事务回滚，并把确定性不可恢复错误映射为不可重试提示。PostgreSQL 集成覆盖调休提交、余额预占、事件、撤销释放和事件失败整事务回滚。

## 9. 审批权限在页面打开后被撤销

**现象：** 如果只在读取任务列表时鉴权，用户可能在权限被撤销后继续使用已经打开的审批页面。

**根因：** 缓存的旧权限状态不能作为写操作依据；前端隐藏按钮更不是安全边界。

**方案：** 写事务先锁定任务和实例，再重新加载用户任职、Capability Grant 和组织范围。并发批准、拒绝和撤回通过行锁与状态机保证单终态。

## 10. Docker、环境变量和并行测试造成的假失败

**现象：** Docker Desktop 通道异常、Windows bind mount、缺少 `.env`、测试数据库权限或 jsdom 资源竞争，都可能表现为“代码坏了”。

**根因：** 代码失败、基础设施失败和验证环境失败没有被分层记录。

**方案：** 健康检查、fresh PostgreSQL、普通 owner 权限、单 worker 前端复跑和独立报告文件分别提供证据。环境失败不会被写成代码缺陷，偶然通过也不会替代完整回归。

## 反复出现的工程原则

1. LLM 负责理解和候选生成，确定性程序负责业务事实和执行。
2. rejected 新候选不能破坏历史可信事实。
3. 前端隐藏不是权限边界，写操作需要事务内重新鉴权。
4. 网络结果模糊时依赖幂等安全重试，而不是猜测请求是否成功。
5. 真实模型评测不是可以反复窥视的调试器；blind 揭示后即降级为 public。
6. 不通过降低门槛、修改分母或删除失败报告包装成功。
7. 先解决真实业务问题，再提炼可复用的 Flow、Draft 和 Approval 抽象。
8. 保留失败证据、环境限制和已知性能债务。
